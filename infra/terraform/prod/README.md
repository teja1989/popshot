# Prod

Two stacks, applied in this order on every deploy by `.github/workflows/deploy.yml`:

1. **`platform/`**: network, Cloud SQL, service accounts, secrets, the database jobs, Firebase.
2. Run the **`db-bootstrap`** job (roles and ownership, ADR 0005), then **`migrate`** (`alembic upgrade head`), both with the new API image.
3. **`services/`**: the Cloud Run `web` (public) and `api` (internal) services.

Migrations finish before new API code takes traffic. Keep them backward compatible with the
previous release (add first, remove later), because the old revision serves until step 3.

## What runs where

| Piece | Details |
|---|---|
| `web` (Cloud Run, public) | Next.js. All egress through the VPC, so it can reach the internal API. Runs as `run-web`, the only identity allowed to invoke `api` |
| `api` (Cloud Run, internal ingress) | FastAPI. Reaches Cloud SQL by private IP, logs in as its IAM user (no password) |
| Cloud SQL Postgres 16 | `db-f1-micro`, single zone, private IP only, TLS required, daily backups (7 kept), point-in-time recovery (7 days), deletion protection |
| `db-bootstrap` job | Runs as `job-db-admin`, the only identity that can read the admin URL secret |
| `migrate` job | Runs as `job-migrate`, IAM login as a member of `popshot_owner` |
| Firebase Auth | Browser API key restricted to the two sign-in APIs and the web app's addresses. Email, phone and anonymous sign-in are off |
| Firebase Hosting | `popshotpb.com` (and `www`, which redirects) in front of `web`; see "Our domain" |
| Budget alert | $25/month, alerts at 50/90/100% (only if `BILLING_ACCOUNT` is set) |

The Cloud SQL admin (`postgres`) password is generated by Terraform but written only to Cloud
SQL and Secret Manager through write-only arguments. It never appears in state, plans or logs.
Rotate it by bumping `admin_password_version`.

## First deploy

`./infra/provision.sh <project-id>` does all of this end to end (see `../bootstrap/README.md`).
By hand:

Prerequisites:
- the bootstrap is applied and the GitHub environments and variables are set (`../bootstrap/README.md`);
- teja1989/popshot#8 (IAM database login) and #9 (container images) are merged, since the jobs and services need them.

1. Merge to `main`. The **Deploy** workflow builds, scans and pushes both images, then plans.
2. Open the run, read the **platform plan** in the summary, and approve the `prod` deployment.
3. After it finishes, do these console steps once:
   - **Firebase console → Authentication → Sign-in method → Google → Enable.** This creates the
     OAuth client. It isn't in Terraform so its secret stays out of state.
   - **Optional, for the budget alert:** in Billing → your account → Account management, grant
     the `gha-deploy` service account **Billing Account Costs Manager**, set the `BILLING_ACCOUNT`
     variable on both environments, and re-run the deploy.
4. Visit the web URL from the run summary and sign in.

## Our domain (popshotpb.com)

Firebase Hosting (`platform/hosting.tf`) sits in front of the Cloud Run `web` service on
`popshotpb.com`: a Google certificate, a CDN, and sign-in's `/__/auth` pages on our own
domain. `www.popshotpb.com` redirects to it. Free; no load balancer.

```
browser ─▶ popshotpb.com (Cloudflare DNS, not proxied) ─▶ Firebase Hosting ─▶ Cloud Run web ─▶ api
```

DNS stays at Cloudflare (Cloudflare Registrar only allows its own DNS), added by hand: about
six records, and no Cloudflare token in CI. The run.app address keeps working alongside.

**After the deploy that adds Hosting** (once):

1. **Cloudflare → popshotpb.com → DNS → Records.** Add every record from the deploy run's
   summary ("DNS records to add at Cloudflare", also `terraform output dns_records`), with
   **Proxy status: DNS only** (grey cloud). Then the "this domain sends and receives no
   email" records, so nobody can send mail as popshotpb.com:

   | Type | Name | Content |
   |---|---|---|
   | MX | `@` | `.` (priority 0) |
   | TXT | `@` | `v=spf1 -all` |
   | TXT | `_dmarc` | `v=DMARC1; p=reject; adkim=s; aspf=s` |

   Don't add CAA records or turn on the orange-cloud proxy: either can stop Firebase issuing
   or renewing the certificate.
2. **Wait for the certificate.** Firebase console → Hosting → the `-web` site → Custom
   domains shows each domain go from "Needs setup" to "Connected". Usually minutes, up to 24
   hours. If Firebase asks for another record (an ownership TXT), the next deploy's summary
   shows it.
3. **Google Cloud console → APIs & Services**, so Google sign-in can run on our domain:
   - **Credentials** → the OAuth 2.0 web client Firebase created ("Web client (auto created
     by Google Service)") → add the authorized JavaScript origin `https://popshotpb.com` and
     the redirect URI `https://popshotpb.com/__/auth/handler`.
   - **OAuth consent screen → Branding → Authorized domains** → add `popshotpb.com`.
4. Check: `curl -I https://popshotpb.com` (a valid certificate, the app's CSP and HSTS
   headers) and `curl -I https://www.popshotpb.com` (a redirect to popshotpb.com).

The app itself moves to the domain in a later change (sign-in, links, push and a redirect
from run.app), once the certificate is live.

## Costs (rough, us-east4)

Cloud SQL `db-f1-micro` with 10 GB SSD and backups: about $10–15/month. Cloud Run scales to
zero. No NAT, no load balancer, no connector; Firebase Hosting costs little or nothing. Expect well under the $25 budget at crew scale.
